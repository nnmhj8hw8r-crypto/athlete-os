# Изменение структуры данных

Данные пользователя живут только в IndexedDB его iPhone. Ошибка миграции = потерянный дневник.
Выполни все шаги, ни один не пропускать.

1. **Схема** — `src/domain/schemas.ts`. Новые поля у существующих записей — только `.optional()`
   (старые записи должны оставаться валидными). Новую таблицу добавить в `ENTITY_SCHEMAS` и
   `TABLE_LABELS`; если она не должна попадать в копию JSON (Blob и т. п.) — не добавлять, описать в
   `src/data/db.ts` и KNOWN_ISSUES.
2. **IndexedDB** — `src/data/db.ts`: НЕ трогать существующие `db.version(N)`. Добавить
   `db.version(N+1).stores({...})` только с изменёнными/новыми таблицами и при необходимости
   `.upgrade(tx => ...)`. Индекс — только по полям, по которым реально ищем (`where(...)`).
   Типы таблиц добавить в `AthleteDb`.
3. **Копии** — `src/domain/backup.ts`: увеличить `DATA_SCHEMA_VERSION` (= N+1) и добавить шаг
   `MIGRATIONS[N]`, который приводит данные копии версии N к N+1 (пустые новые таблицы, перенос полей) —
   тем же преобразованием, что `.upgrade` в db.ts. Общую логику вынести в `src/domain/` и вызвать из обоих мест.
4. **Тесты**:
   - `src/test/fixtures.ts` — черновик для новой таблицы (иначе CRUD-тест не соберётся);
   - `src/domain/backup.test.ts` — `fullData()` с новой таблицей, число записей, тест «копия версии N импортируется»;
   - `src/data/repo.test.ts` — тест обновления базы N → N+1 на fake-indexeddb: создать `new Dexie(name)` с
     версиями 1..N и данными, открыть `openDb(name)`, проверить результат `.upgrade`;
   - тест «схема IndexedDB совпадает с версией формата копии» должен проходить сам.
5. **Документы**: `docs/DECISIONS.md` — новое решение «Данные версии N+1» (что добавлено, почему, как
   мигрирует); `docs/ARCHITECTURE.md` — таблица «Данные» и «Версии схемы данных».
6. `npm run check`. Вручную в браузере: открыть приложение с данными старой версии (до изменений) и
   убедиться, что после обновления всё на месте.
